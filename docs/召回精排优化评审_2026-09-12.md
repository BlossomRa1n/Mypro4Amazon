## 1. 优先级判断

建议把下一阶段顺序调整为：**修复数据与评估正确性 → 建立可复现基线 → 候选融合与精排训练分布对齐 → 模型结构实验**。

多路互补、全库评估和逐变量消融值得保留。但目前代码中存在足以改变实验结论的缺陷，因此不宜把 AUC=0.7417、HR@100=13.76% 等历史数字直接作为后续不可退让的门槛。应保留历史记录，修复后另建基线。

当前本地版本与汇报不完全一致：

- `DINExtendedDataset` 仍将每个负样本展开成一条 `(uid, pid, neg)`，训练调用 `forward_pairwise`，没有汇报中的 Stage A 多负样本打包与 `forward_bpr`。
- `DINTokenizedModel` 仍保留 item 加权求和、投影和 LayerNorm，不是汇报中的 raw-slice 版本，也不是完整的 3a-3 版本。
- `config.py` 的召回权重仍为 `[1.5, 1.0, 0.7, 0.05]`，并非调参得到的 `[1.5, 3.0, 1.0, 0.05]`。
- 本地没有 Stage A/B summary、Phase 2 专用 checkpoint 和最新 DIN-Ext checkpoint。不能根据本地文件确认服务器实验的最终结果或实际使用的代码。

汇报中的执行计划仅作为评审材料，本次没有据此启动服务器、训练、自动关机或下载。

## 2. 必须先处理的代码问题

### P1：SVD 初始化使用了验证集交互

证据：`code/train_v2.py:238`、`code/train_din_ext.py:410`、`code/train_hstu.py:166`、`code/train_mind.py:257`、`code/train_din_token.py:97` 均从完整 `click_df` 提取正样本进行初始化，而非 `train_click`。

`code/als_init.py:98` 又会直接复用已有缓存，不验证数据切分和编码映射。当前代码从零生成缓存时会把验证交互带入 SVD；已有缓存是否污染，取决于它的实际生成过程，不能仅凭文件名判断。

建议：只用训练允许的交互拟合 SVD，并为 SVD、ItemCF、checkpoint、item embedding 记录数据切分标识、编码映射 hash、配置和代码版本。修复调用后必须生成新的缓存，旧缓存保留归档。不能只换 checkpoint 路径而沿用来源不明的 item embedding。

补充：`code/data_loader_ext.py:513` 的商品平均评分、评分总数来自 raw meta 快照，历史 helpful_vote 也是累计值。它们不是随预测时间更新的历史特征。严格时间评估应按截止时间重算可重算的统计；无法还原历史的字段先移除做对照。`code/inference_full.py:439` 等路径的热门统计也用了全量数据，全局统计同样可能泄漏未来信息。

### P1：训练目标出现在输入历史中

证据：`code/data_loader.py:564` 保存每条训练交互，`:614` 按用户保存完整训练历史，`:680` 不依赖目标位置取出该历史。DIN 同样在 `code/data_loader_ext.py:780` 缓存完整历史，在 `:949` 按用户取出。

例如，训练历史为 `[a,b,c,d]`，预测 `b` 时输入仍是 `[a,b,c,d]`，同时包含目标和目标之后的事件。SASRec block 的 causal mask 不能修复这个问题，因为最终用户表示对整段序列做池化；DIN target attention 更容易利用“目标已在历史里”的捷径。这是训练任务与未来推荐任务不一致，不等同于验证历史直接包含验证标签。

本次小样本验证：DIN 和 V2 的目标索引均为 `1`，输入历史均为 `[0,1,2,3]`。

建议：构造 `(user, cutoff, history_before_cutoff, target)`，历史与用户统计都来自 cutoff 之前。序列召回可采用 shifted next-item 训练；DIN 可采用前缀预测下一条正反馈。先定义是否允许重复购买，不能仅用“从历史中删除目标 ID”替代时间截断。

### P1：真实 ID 与 padding=0 冲突

证据：`code/data_loader_ext.py:435` 的商品 LabelEncoder 从真实商品开始编码；品牌和品类虽然加入了 `__PAD__`，LabelEncoder 会排序，并不保证该符号位于 0。`code/model_ext.py:127` 等 embedding 却设置 `padding_idx=0`，序列 mask 也把 0 当作无效项。

本次验证中索引 0 分别为真实用户 `u0`、商品 `a`、品牌 `Acme`、品类 `CDs_and_Vinyl`。因此问题不限于一个商品：一个真实品类可能失去可训练的品类向量。商品 0 还会被当作 padding 屏蔽，并被从索引 1 开始的负采样排除。

建议：显式固定 PAD=0、UNK=1、真实实体从 2 开始；或者不需要 padding 的用户 ID 层取消 padding 语义。映射变化必须同步重建相关模型和产物，禁止把旧 embedding 直接按新行号加载。增加 PAD、UNK、真实 ID 的往返映射与 mask 检查。

### P1：精排 AUC 计算与声称的协议不一致

证据：`code/train_din_ext.py:287` 使用 `pos_arr[:, None] > neg_arr[None, :]`，让每个用户的正分数与所有用户的负分数比较。它近似 pooled AUC 的严格大于版本，并不是文档描述的用户内 pairwise AUC；相同分数也没有计 0.5。

本次验证：两个用户分别为 `0.9 > 0.8`、`0.2 > 0.1`，用户内排序全部正确，但当前公式得到 0.75。BPR 不约束不同用户之间的整体分数偏移，故跨用户 AUC 尤其不适合作为唯一选模依据。

此外，`:214` 的 `default_rng()` 未设置种子，`:269` 没有排除目标和已知正样本，验证历史默认只有 5 条，而训练与推理使用 50 条。用户采样也随全局随机状态变化。将人数直接提高到 10 万、每人 50 个负样本时，当前比较矩阵约需 500 GB 的布尔数组内存。

建议：固定用户列表与负样本文件，把负分数保存为 `[U,K]`，按用户计算比较和 ties；统一历史长度。随机负 AUC 仅作辅助诊断，选模依据改为固定召回候选池上的 HR@5、NDCG@5。真正需要 pooled ROC AUC 时使用标准实现并明确命名。

### P1：断点续训时优化器没有绑定恢复后的模型

证据：`code/train_din_ext.py:81` 在 `_load_checkpoint` 内创建新模型，但优化器由调用方基于旧模型创建。正常兼容分支没有重建优化器。`train_v2.py`、`train_hstu.py` 有同类实现；token 训练复用 DIN 的恢复函数。

本次调用真实恢复函数、使用内存模拟 checkpoint 验证：模型参数与 optimizer 参数对象不同，反向传播并 `optimizer.step()` 后，新模型权重从 1.0 仍为 1.0。

建议：先恢复模型，再构造绑定该模型的 optimizer 和 scheduler，最后恢复相应状态。latest checkpoint 应保存 optimizer、scheduler、AMP scaler、随机状态和 best 指标。当前多处 latest 保存仍传 `save_optimizer=False`，不具备完整续训语义。恢复后至少验证一次实际权重更新，并与连续训练做短程对拍。

### P1：并集精排实验同时改变了候选和评分规则

证据：`code/inference_full.py:240` 固定使用：

```text
final = 0.7 * sigmoid(DIN_logit) + 0.3 * recall_score / (abs(recall_score) + 1)
```

`code/measure_union_rerank.py:49` 的并集分数改成跨通道最高倒数排名；baseline 则使用原始召回加权分数。因此文档中的 0.719% → 1.306% 是两个完整配置的差异，不能完全归因于“并集扩大”或“DIN 更好利用互补信息”。BPR 分数经 sigmoid 后也不是经过校准的购买概率。

建议在两个候选池上分别测三种排序：召回排序、纯 DIN logits 排序、使用统一召回特征的融合排序。池大小和评分规则分开做消融；保留每用户候选数、命中标签和输出，才能解释提升来自哪里。

### P2：召回融合存在候选预算浪费和过滤不一致

证据：`code/recall_fusion.py:324` 先给各通道分配 quota，`:337` 先截断再合并，去重后不补足。实际并非对全部候选简单加权求和。本次验证：两路各有相同的 100 个商品，等权融合请求 100 个，最终只返回 50 个。

`:215` 的向量召回只排除截断后的历史；`evaluate.py:219` 排除完整训练交互；品类和热门通道没有相同的已见过滤。这会造成独立评估与融合评估的候选口径差异。

建议：共享候选资格和 seen-set 规则，显式排除 PAD、不可推荐实体；去重后回填到固定预算。分别报告“原始并集覆盖率”和“固定 100 候选覆盖率”。先解决这些问题，再评价六路融合是否不如四路。

## 3. 先统一评估问题，再重建结果表

当前 `split_train_val` 是用户内 80/20 切分；召回与最终 HR 使用后 20% 的正反馈集合，DIN AUC 只取该集合最后一条。它不等于标准 leave-last-out。部分 NDCG 实现只累计 DCG、没有除以多目标 IDCG；见 `code/evaluate.py:239` 与 `code/tune_recall_weights_6ch.py:164` 附近。

建议选择一个主任务：

- 下一件喜欢的商品：历史预测一个后续目标，明确 val/test 留出规则。
- 未来窗口推荐：历史预测未来一段时间的多个正反馈，使用规范的多目标 HR、Recall、NDCG。

两者都可以做，但不能共用指标名称而混比。主实验保留一个未参与选模型和调权的时间测试集；用户内时间切分也不等于全局时间回测，模拟部署时另做全局 cutoff 实验。

评估表建议包含：候选数均值与分位数、候选覆盖率、端到端 HR@5/NDCG@5、召回命中用户内的排序成功率、耗时与峰值显存，以及短历史/长历史、热门/长尾、品类和冷启动分组。

当 Top-5 完全取自候选池、用户与标签口径一致时：

```text
端到端 HR@5 = 候选命中率 × P(Top-5 命中 | 候选池命中)
```

兜底额外加入池外商品时，先将其纳入候选定义。22.02% 的数百候选并集覆盖率不能标作固定 HR@100，也不能直接当作融合 Top-100 可达到的成绩。

保留固定 10 万用户做调参有价值，但小幅收益用同用户 paired bootstrap 或命中差异分析，并对入围方案运行多个训练种子。协议修复导致旧指标下降并不代表优化失败。

## 4. 最值得投入的召回优化

### 第一优先：兑现现有通道的候选价值

1. 绑定模型、item embedding、特征快照和 encoder 为同一个实验产物；修复硬编码的 best 路径。Phase 2 checkpoint 必须配套重新导出的向量，不能只换用户塔。
2. 测试去重回填的 quota 和 RRF，作为低成本融合基线。RRF 对跨路原始分数尺度不敏感，但仍须以实验确认收益。
3. 保留每路 score、rank、是否命中、通道数量、品类匹配和训练期热度，使用轻量学习排序，例如 LightGBM LambdaMART，对并集做 300~400 → 100 的粗排。
4. 训练融合器的候选必须由对应时间之前训练的召回器产生。用滚动时间窗口构造训练候选，在独立验证集调参，避免召回器已看过融合训练目标的泄漏和样本分布偏差。

当前六路搜索固定了四路最优权重，再加 HSTU/MIND；新通道会改变所有 quota，此时旧四路最优未必仍最优。`tune_recall_weights_6ch.py:374` 的新通道搜索也没有 0 权重对照。因此 13.58% 只能说明当前搜索范围和融合实现下未获益，不能否定六路加权融合这一类方法。

### 第二优先：修正单路学习目标与廉价结构问题

- InfoNCE：`code/model.py:401` 只认对角线为正样本，没有屏蔽 batch 内重复商品、同用户的其他正样本。先统计冲突率，屏蔽确定的假负样本或采用多正例目标；难负采样同样排除当前目标和训练中已知正反馈。
- MIND：`code/model.py:602` 要求每个兴趣胶囊都拟合同一个目标，可能促使兴趣趋同。比较 label-aware target assignment 或 max/logsumexp 多兴趣目标，监控兴趣间余弦相似度和 Top-K 重叠。推理合并按胶囊顺序截断也会偏向前几个兴趣，可比较按最高相似度合并或均衡轮询。
- 时间衰减：`code/model.py:181` 将当前 gap 也计入 recency。对于 `[0,0.25,1]`，得到 `[1.25,1.25,1]`，正确的距最后事件间隔为 `[1.25,1,0]`。建议直接从时间戳计算 age，并用具有明确单位的半衰期，避免每用户最大 gap 归一化掩盖真实时间尺度。
- ItemCF：目前相似度衰减尺度为 1 天，召回历史衰减尺度为 7 天，先与 Amazon 实际购买间隔对照，再实验 7/30/90 天及无衰减。当前 `exp(-dt/tau)` 中 tau 是 e-folding 时间，若称半衰期，应使用 `exp(-ln(2)*dt/half_life)`。缓存每个 item 的有序邻居，避免对每个用户重复全量排序。
- 新通道优先考虑低成本内容特征：标题、品牌、品类等与纯协同信息互补。先测按 parent_asin 的实际元数据覆盖率；JSONL 中 verified 为真的比例并非 join 匹配率，不能据此推断 title 也无法匹配。

### 需要更正的架构结论

`code/model.py:243` 的 `q*k → cumsum → v gate` 是自定义因果门控结构，不是原始 HSTU 中基于跨位置 QK 相似度的注意力实现。可以保留它作为有效通道，但应准确命名，不能把该实验当作标准 HSTU 复现。报告复杂度时还应计入 Linear 投影的成本。

`code/als_init.py:223` 先更新 `E_user`，再用新 `E_user` 更新 `E_item`，不是同一层分别从上一层传播的标准 LightGCN 更新。当前实验只能否定这个实现和配置的 warm-start，不能据此断定 LightGCN 普遍无效或把下降归因为过平滑。无需立即重做，但应收窄结论。

## 5. 精排建议：先改变任务对齐，再考虑更复杂模型

### 用真实候选训练精排

当前训练主要区分“正反馈商品”和“随机商品”，推理却要在各召回器筛选出的相似商品之间选择。把随机负样本从 4 增到 8 可以作为实验，但未必能改善真正的候选内排序。

建议从训练期时间窗口构建真实召回候选，采用随机负样本与召回负样本的混合，并给假负样本保留不确定性。不要使用独立验证或测试标签来清洗训练负样本。没有曝光日志时，未交互商品只能作为采样负例，不能声称是已曝光未购买。

固定候选池下，至少比较：召回原排序、轻量 LambdaMART、修正后的 DIN。DIN 显式加入各通道分数、排名和来源特征，让模型学习何时相信各路召回，而不是仅在输出端固定 0.7/0.3 混分。可比较 BPR 与按同一用户候选集合归一化的 listwise loss。

### 保留 raw-slice，但把它作为等价重构验收

把基线特征原样拆分再拼接，同时复制相同参数、保留 feature 顺序、BatchNorm 状态和激活，理论上可以与原模型完全等价。应先在 eval 模式验证 logits，再在控制随机性的条件下比较 loss、梯度和一次参数更新。

因此 Step 1 不需要先花一次完整训练去追 AUC≈0.74，更不应用 0.72 作为“无损”标准。若 feature 顺序改变，需要相应置换第一层权重；若删掉 verified 分支或改变 dense 维度，就已经不是单纯切片重构。

“随机投影打乱 CF 信号”目前只能作为假设。256→256 的可学习线性层不必然损失信息；压缩、LayerNorm 去除尺度、求和丢失来源、优化难度、初始化、训练样本与评估差异都可能参与退化。把同一投影从 token 定义移到 mixer 内，若计算图不变，也不会自动改善结果。

建议保留 raw 特征直连主支路，为 mixer 增加初始输出为零的残差分支，保证起点与基线一致，再检验新增交互是否产生增益。不要预设 RankMixer 一定会超越基线。

### 调整六步计划中的具体选择

- User warm-start：比较随机初始化、同次 SVD 的 `U*Sigma` 配 `V`、平衡分解 `U*sqrt(Sigma)` 配 `V*sqrt(Sigma)`。若继续对 item 行向量归一化，内积已不再等于原低秩重建。保留用户模长可能保留活跃度，也可能强化流行度偏差，不能称为唯一正确版本。
- 品类维度：16/32 是合理实验。44×256 约 1.1 万 embedding 参数，本身并非主要内存来源；83 万×256 的 user embedding 才约 2.13 亿参数。优先比较 DIN 删除或缩小 user ID embedding、改用历史画像，但召回删 user ID 的收益不能直接外推到精排。
- Dense：当前 rating_number、helpful 已有 log 变换。重点是训练期拟合并保存变换参数，对 click_count、time_span 检验 log1p/裁剪/标准化，保留缺失标记，避免重复变换。
- Mixer：工作汇报写 token self-attention，设计文档写 MLP token mixing，二者不是同一个结构。明确选一个小模型，与同参数预算 MLP/DCNv2 作对照，再决定是否扩大。
- MoE：推迟。当前瓶颈尚不能归结为模型容量，MoE 会增加训练、路由与推理复杂度。只有简单模型在正确任务上已稳定、分群误差显示可利用差异时再投入。
- Perceiver：若候选打分是实际耗时瓶颈，可再比较缓存用户记忆；真实有效历史很短时，16 个 latent slot 未必比直接 DIN 更省。用 profiler 和实测延迟判断，不能把注意力对数比值直接视为端到端加速倍数。

### Stage A/B 的验收注意点

可复用的是候选无关的历史 embedding、用户画像等；DIN target attention 本身仍依赖每个候选，不能直接跨候选共享最终兴趣向量。

Stage A 的 eval logits 对拍只能验证确定性前向。基线有 BatchNorm 和 Dropout，改变正负样本打包、正样本重复次数及 optimizer step 数可能改变训练行为。对照需报告正样本曝光数、负样本数、更新次数、学习率调度和吞吐。Stage B 4→8 应比较同正样本训练量，并另外报告同训练时间预算的效果。

## 6. 建议实验顺序与验收

| 顺序 | 工作 | 验收依据 |
|---|---|---|
| 0 | 同步服务器 Stage A/B 代码、配置、summary 与产物来源 | 每个数字能对应唯一代码和配置；确认正常完成与是否续训 |
| 1 | 修正前缀样本、SVD/统计边界、PAD、AUC、续训 | 小样本不变量与恢复权重更新验证通过 |
| 2 | 固定 val/test、候选资格、产物版本，重跑 ItemCF/V2/DIN | 得到同口径的新基线，不用旧数字硬性 gate |
| 3 | 去重回填、RRF、统一混分规则，固定预算与扩大预算分别对比 | 候选覆盖、HR@5、NDCG@5 与延迟一起报告 |
| 4 | 候选分布对齐；LambdaMART 与 DIN+召回特征 | 对固定候选池上的纯召回排序产生可重复增益 |
| 5 | raw-slice 等价重构、简单残差 mixer | 等价验证通过，新增分支在独立验证集上有效 |
| 6 | MIND 目标改进、内容召回、MoE/生成式召回等 | 根据剩余误差与计算预算择一推进 |

工程上建议用每次实验独立目录保存 config、metrics、checkpoint 和 artifact manifest，数据路径改为配置或环境变量。统一训练与推理的特征装配函数，统一评估入口，避免多个脚本各自复制一份不一致逻辑。
