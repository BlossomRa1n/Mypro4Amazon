## 1. 为什么能从 17,296 扩大到 100,000

原月度审计对 Stage A/B 采用了 **774,585 人完整旧验证母体**作为保守排除，因为没有保存原逐次评估用户名单。本次进一步检查运行前 Git、执行补丁、启动配置和日志，发现可以确定性重建抽样。

1. Git `cd242887b0e22d2cb2396bf9ce0b1832340d4c50` 时间为 9 月 8 日，早于 9 月 10 日的 Stage A/B，已经包含 `set_seed(42)` 与 `np.random.seed(42)`。不是运行后才补的 seed。
2. 对这个 Git 版本在内存中应用归档 Stage A trainer/dataset/metric 补丁，结果与服务器归档源码完全相同。母体编码覆盖、历史资格和用户排序也可由该源码与原数据身份重建闭合。
3. 训练负采样、评估负采样及 SVD 使用独立 RNG 或已缓存资产；Torch 训练不消费父进程 NumPy 全局 RNG。每个 epoch 的用户抽样是该主进程唯一相关的全局 RNG 消费。
4. 两阶段分别启动新 Python 进程，每次 seed 42、两 epoch、每 epoch 无放回抽 10,000 人。它们使用同一升序母体，故抽样相同。两次 draw 去重并集是 **19,878 人**。

两个独立实现复算该并集完全一致。主代理又独立重放抽样、复建全部原 296 项历史身份来源，并核对新 test 的抽样、资格、边界及互斥。

此前“没有 RNG 快照，因此无法精确恢复”是过度保守的判断；运行前源码、可复原补丁链及明确 RNG 控制流提供了新的恢复依据。**17,296 是原保守证书的容量，不是数据本身无法突破的上限。**

## 4. 证据边界与正式使用前的工作

StageAB 名单是依据运行前源码与日志的**确定性重建**，不是找回原始逐次评估数组。原始运行时 RNG 快照、逐次用户数组和 NumPy 精确版本未保存；复算依据 legacy `RandomState` 的固定 seed/调用序列兼容保证。本次仅替换已审核的特定历史来源，不据此声明覆盖任意未知实验。

“未用于选型”的历史范围仍按用户批准的本月范围处理，六月实验不作为排除条件。身份隔离本身也不证明所有特征、召回资产和训练统计都满足严格时间因果；它们仍属于下一项训练退化诊断的审计范围。

正式使用前需完成：

1. 将本名单、修订来源和新协议绑定；保留旧 v3，不能直接改其文件或把新名单塞入旧 `all_fresh` 守卫。
2. 在训练退化诊断 runner 中明确支持固定 100k manifest，验证身份、数量、资格、互斥、历史来源、数据资产和 SHA，禁止静默截断或重抽。
3. 开发诊断只用固定 screen/confirm；继续封存 test。训练、负例、停止点和最终模型选择规则确定后才安排一次最终验收。

下一步仍是训练退化诊断，暂缓新增 cross/token 消融。人数问题的解决不改变这个优先级。

## 5. 其他路线的调查结论

已经找到不改变数据分布的恢复路径，因此本次没有采用成本更高的备选方案：

| 路线 | 可行性与限制 |
|---|---|
| 同五品类 raw JSONL 中、未进入 5-core CSV 的用户 | 可在无卡服务器流式计数；可能补足新用户，但更稀疏，须保持历史资格与身份排除，不能保证人数或代表性。加入用户/商品需要重新审计编码和训练资产。 |
| 新增品类或真正未用过的新时期 | 可建立新的隔离测试，但改变数据分布或时间协议，须同步建立匹配的开发基线。当前 CSV 已全量使用，future20 一直到每用户最后记录，不能再切其末 10% 并称为未使用时期。 |
| 完全重新切分、重训现有数据 | 可以建立新的固定工程验收集，但重训不会清除旧标签曾参与选型的事实；需要如实标记复用，并重建所有受新时间边界影响的特征、召回、SVD/V2和精排资产。当前无需采用。 |
