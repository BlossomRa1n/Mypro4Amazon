# Corrected Baseline Protocol

The new authoritative entry point is `code/run_baseline.py`. The primary business metric is future-window Top-5 hit rate: users are given a strict 80% prefix and the target is the set of positive products in the remaining 20% window. The single-target leave-two-out metric used by the first corrected run remains an auxiliary diagnostic. Historical training scripts and their artifacts are retained for traceability; they are not the entry points for this corrected benchmark. Existing numerical results must not be compared as if they used this protocol.

## Task and Data

- Five configured Amazon categories; ratings >= 4 are positive observations. This predicts future positive review behavior, not calibrated purchase probability.
- Keep the earliest positive interaction per user/product. Sort by user, timestamp and product ID deterministically.
- For the primary business evaluation, split each eligible user at a strict 80% timestamp prefix and evaluate all unique positive products in the following 20% window. The auxiliary diagnostic holds out the penultimate and final events.
- Training uses strictly earlier user history; simultaneous events never enter the target's history. Test histories may include the observed validation event, but test labels are never used for training or checkpoint selection.
- PAD=0, UNK=1, real entity IDs start at 2. The catalog is transductively known, including IDs without training interactions. Report this explicitly; this is not a global time-cutoff deployment simulation.
- Item category is the CSV source category. Brand uses static metadata where available. Historical metadata availability is assumed; future aggregate rating counts, helpful votes and verified snapshots are not consumed.
- SVD, ItemCF, popularity, item rating aggregates and scaling constants are fitted on training interactions only. User statistics are computed from the sample prefix. Item aggregates are training-corpus statistics, not per-event global historical snapshots.

## Models and Candidates

- ItemCF: train-only cosine co-occurrence with inverse user-frequency weighting, top-100 stored neighbors, up to 50 recent observed products as query history. This deliberately establishes a standard, reproducible ItemCF baseline instead of reusing the old time-decayed cache.
- V2: existing SASRec model, item-only train SVD initialization, brand preference and corrected time-decay pooling. InfoNCE excludes duplicate target IDs, same-user batch collisions and known prefix positives; explicit uniform training-catalog negatives exclude the user's known training positives.
- DIN: existing DINExtendedModel, server's shared user encoding, packed four negatives, one mixed positive/negative scoring batch for BatchNorm. BPR uses stable softplus and BF16 training on CUDA. No new mixer or learned fusion model.
- Four-channel quota fusion uses preregistered weights 1.5/1.0/0.7/0.05. Duplicate removal is followed by refill. All channels exclude the full observed history, PAD and UNK. Weights are not tuned on test.
- Pure DIN logits determine final ranking. No fixed sigmoid/recall-score blend. Score-only baseline and DIN use identical candidate pools.
- Evaluation uses FP32 model scores, including DIN, to avoid BF16 quantization introducing extra ranking ties.

## Evaluation and Reproducibility

- Fixed seed 42. Validation subset: 10,000 users for checkpoint selection. Final validation/test: fixed 100,000 users by default; `--final-users 0` evaluates all eligible users.
- V2 checkpoint selection: primary future-window validation HR@100. DIN checkpoint selection: primary future-window HR@5 on a fixed pool generated by the selected V2 and train-only ItemCF. Auxiliary single-target metrics are reported separately.
- Report HR, normalized NDCG and Recall for ItemCF/V2/candidate pools; HR@5 and NDCG@5 for recall-only and pure DIN. Also report candidate counts and conditional ranking success given a candidate hit.
- Candidate and random-negative AUC are different diagnostics; global cross-user AUC is not a selection metric. `baseline_runtime.pair_auc` implements within-user comparisons with half credit for ties.
- Fixed initial budget: three epochs for V2 and DIN. Every epoch is recorded. This is a reproducible initial baseline, not a claim of hyperparameter optimality or convergence.
- Each run directory contains data/config/code identities, distinct best and full-state latest checkpoints, epoch histories, predictions and final metrics. A mismatch aborts resume. A full run writes `COMPLETED.json` with `status=complete` only after both final split evaluations finish. A `--validation-only` run writes `status=validation-only`, lists only the `val` split, and must not be treated as a final test result.
- A restart uses the exact same command. Completed epochs are skipped, optimizer/scheduler/RNG states are restored, and best models are used for inference. Partial epochs restart from the last complete epoch.
