## 1. 项目背景与当前架构

Amazon Reviews 2023 推荐系统，召回 + 精排两阶段。当前召回为四路融合：

| 通道 | 权重（`config.RECALL_WEIGHTS`） | 读法 |
|---|---|---|
| ItemCF | 1.2 | 物品协同过滤（共现 + 时间衰减） |
| V2 SASRec | 2.2 | 双塔向量内积（Transformer 因果自注意力） |
| Category | 0.5 | 品类偏好热门 |
| Hot | 0.1 | 全局热门兜底 |

融合逻辑：`recall_fusion.py` 的 `merge_recall_results`（每路按权重分配名额，floor=3 保底），`multi_channel_recall` 编排四路。

数据：`Video_Games`，CSV 5-core 统一管道（约 94K 用户 / 25K 商品，与 raw_meta JSONL 的 brand/quality 特征 merge）。序列很短：平均历史 7.1 条、中位数 4 条。

---

## 2. 概念澄清（重要）

**HSTU / SASRec / MIND ≠ 生成式召回**。三者本质都是序列推荐 / embedding 检索：把用户编码成向量，和商品向量做内积取 Top-K，输出是"分数"。

**生成式召回（Generative Retrieval / TIGER 范式，Rajput et al., RecSys 2023）** 是范式级差异：用 decoder-only Transformer **逐 token 生成商品的语义 ID**，像生成句子一样生成候选列表。

```
双塔召回:   用户历史 → encode → user_vec ──dot── item_vec → top-k
生成式召回: 用户历史 → encode → 自回归 decode "c1 c2 c3" → beam search → top-k
```

本项目已有的三样资产正好是 TIGER 的全部原料（见第 5 节）。

---

## 3. 目标与约束

**目标**：新增一条生成式召回通道，为召回并集提供与向量内积互补的候选。

**约束（硬）**：

- 纯增量，不动现有四路。
- 时序分割防泄露（只用 `train_click` 训练窗口）。
- 短序列（median 4 条）是所有生成式方案的共同瓶颈。
- 输出空间必须压缩：直接生成 `item_idx`（25K~137K 词汇表）不可行（见方案 C）。

## 4. 方案对比

| 方案 | 语义 ID 来源 | 生成模型 | 工程量 | 语义结构 | 推荐度 |
|---|---|---|---|---|---|
| **A. 完整 TIGER** | RQ-VAE 残差量化 | decoder-only Transformer | 最大 | 强（端到端学） | 二选 |
| **B. 轻量 TIGER** | 层次 K-means 聚类 | decoder-only Transformer | 中 | 中（粗→细分层） | ⭐ 推荐 |
| **C. 直接 item_idx** | 无（原始商品 ID） | decoder-only Transformer | 最小 | 无（随机 ID） | 仅作 baseline |
| **D. 文本语义 ID** | 标题 embedding + 量化 | decoder-only Transformer | 大 | 最强（跨模态） | 暂缓 |

四者生成模型相同，差异全在"语义 ID 怎么造"。

### 4.1 方案 A：完整 TIGER（RQ-VAE 语义 ID + 自回归）

- **理由**：生成式召回的正宗范式，学术认可度最高。
- **做法**：用 RQ-VAE 把 `item_embeddings_v2.pkl`（N × 256）残差量化为 3 个离散 code，decoder 自回归生成。
- **优点**：前沿叙事最强；RQ-VAE 端到端优化重建，语义 ID 分层质量最好；输出空间 O(商品数)→O(codebook=256)。
- **缺点**：工程量最大（RQ-VAE + 生成模型 + beam search + 融合接入四个组件）；新增依赖 `vector-quantize-pytorch`；RQ-VAE 需调参（codebook 尺寸/层数/decay/commitment loss 权重），量化阶段易翻车。

### 4.2 方案 B：轻量 TIGER（层次 K-means 语义 ID + 自回归）⭐

- **理由**：保留 TIGER 全部范式收益，把最容易翻车的 RQ-VAE 换成无参、稳定的层次 K-means。
- **做法**：对 `item_embeddings_v2.pkl` 做三级层次聚类得到 `(code1, code2, code3)`。
- **优点**：零新依赖（sklearn/numpy 即可）；直接复用已验证的 SASRec item embedding；工程量约为 A 的 60%；生成模型与 A 完全共用，后续可局部升级到 RQ-VAE。
- **缺点**：K-means 硬量化无端到端重建优化，语义 ID 质量略低；层次聚类是贪心的，上层误差传导下层；需处理空组/单点组。

### 4.3 方案 C：直接 item_idx 生成（无语义 ID）

- **理由**：最简，省掉量化组件；价值在作 ablation baseline 量化语义 ID 增益。
- **缺点（致命）**：词汇表 25K~137K，输出 softmax 层巨大且每步全量计算；`item_idx` 是 `LabelEncoder` 按首次出现顺序分配，无任何语义结构；长尾商品生成概率趋近 0，退化成热门推荐。**TIGER 论文已证伪此路线。**

### 4.4 方案 D：文本语义 ID（标题 embedding + 量化 + 生成）

- **理由**：语义最强，冷启动商品也能有语义 ID；与双塔跨模态，互补性理论上最高。
- **缺点（硬伤）**：需下载 raw_meta 的 title（~500MB）+ `sentence-transformers`；**数据版本不一致是已知问题**——CSV 5-core 与 raw_meta 的 verified 匹配率仅 11.6%，title 匹配很可能同样对不上。当前不宜作为第一步。

| `multi_channel_recall` | `recall_fusion.py:333` | 召回编排 | 新增第 5 路的接入点 |

**返回格式对齐要求**：所有召回函数返回 `{user_id: {item_id: score}}` 或 `{user_id: [(item_id, score), ...]}`，`merge_recall_results` 两种都兼容。

**关键事实（生成代码前验证）**：`item_embeddings_v2.pkl` 的实际行数 = 语义 ID 覆盖的商品数。历史记录里该值约 25K（CSV 5-core 统一管道）。无论 25K 还是 137K，256³≈16.7M 的语义 ID 容量都足够（占用率 <1%）。

## 6. 推荐：方案 B（轻量 TIGER）

**三条推荐理由**：

1. **用 60% 工程量验证 80% 的核心假设。** 真正的未知数是"生成式读法 vs 双塔内积读法，互补性能否兑现成并集增益"，方案 B 最快回答它。
2. **风险前置最小化。** RQ-VAE 是独立风险源，可能因量化没调好让实验得出"生成式召回没用"的错误结论（那其实只否定了 RQ-VAE，没否定范式）。K-means 无参、稳定，排除这个干扰变量，归因更干净。
3. **渐进可升级。** B 与 A 共用生成模型 + beam search + 训练/推理/接入代码。若 B 验证互补性高，把语义 ID 来源从 K-means 换成 RQ-VAE 是局部替换，不是推倒重来。

**为什么不是最正宗的 A**：A 的价值集中在"前沿接轨"叙事，但它的边际收益（RQ-VAE 比 K-means 好多少）必须等"生成式范式本身有没有增益"验证了才值得投入。先 B 后 A 是把"前沿"与"止损"解耦的正确顺序。

## 7. 方案 B 落地规格（供 AI 生成代码）

### 7.1 模块结构（新增文件，均放 `code/`）

```
code/gen_semantic_id.py   # 阶段 1：层次 K-means 造语义 ID
code/tiger_model.py       # 阶段 2：decoder-only 生成模型
code/train_tiger.py       # 阶段 2：训练脚本
code/gen_recall.py        # 阶段 3：beam search 召回函数（或并入 recall_fusion.py）
```

### 7.2 阶段 1：造语义 ID（纯离线）

**输入**：`item_embeddings_v2.pkl`（N × 256，float32）。
**输出**：`user_data/model_data/tiger_semantic_ids.pkl`，内含：

- `item2sid`：`np.ndarray` 形状 (N, 3)，dtype int，每行是 `(code1, code2, code3)`。
- `sid2item`：`dict`，key 为 `(code1, code2, code3)` 元组，value 为 `item_idx`（用于推理时 token→商品反查）。
- 若多个 item 落到同一语义 ID（碰撞），`sid2item` 只保留其一，并在文档中记录碰撞率。

**逻辑**：

1. 第 1 层：对全部 N 个 embedding 跑 `KMeans(n_clusters=256)` → `code1`。
2. 第 2 层：对每个 `code1` 类内（样本数 ≥ 2 的）再跑 `KMeans(256)` → `code2`；单点组 `code2` 恒为 0。
3. 第 3 层：对每个 `(code1, code2)` 组内（样本数 ≥ 2 的）再跑 `KMeans(256)` → `code3`。
4. 空组不聚类；K-means 用 `random_state=42` 保证可复现。

**验收标准**：可视化 `code1` 的分布——若同品类（如主机游戏）商品倾向共享 `code1`，说明 embedding 本身有语义，继续；若 `code1` 近似均匀随机分布，说明 embedding 缺语义，**止损**，不要继续后续阶段。

### 7.3 阶段 2：生成模型与训练

**模型规格（`tiger_model.py`）**：

- decoder-only Transformer：`embed_dim=256`，3 层，4 头，`dropout=0.1`。
- `vocab_size = 256`（codebook 大小），**不是商品数**。
- 组件：token embedding（256×256）、position embedding、N 个 causal attention block（可参考 `SASRecBlock` 的因果掩码思路）、`lm_head`（256→256）。
- 输入：语义 ID token 序列；输出：每个位置的 next-token logits。

**训练数据流（`train_tiger.py`）**：

1. 加载 `click_df` → `split_train_val` 取 `train_click`（时序防泄露）。
2. 用 `build_extended_user_features` 得到每用户历史 `hist_items`。
3. 把每个历史 item 的 `item_idx` 通过 `item2sid` 映射成 `(c1,c2,c3)`，展平成 token 序列。
4. 训练样本：输入 `[token_{t-1}]`，标签 `[token_t]`，标准 next-token 交叉熵损失。
5. 先 `offline=True` + `AMAZON_SAMPLE_USERS=5000` 验证 loss 下降、能生成合法 ID；再全量。

**验收标准**：验证集上，beam search 生成的语义 ID 能反查回真实商品，且 Top-20 里出现验证集 ground truth 的比例（HR@20）显著高于随机。

### 7.4 阶段 3：接入召回（纯增量）

**新增 `generative_recall` 函数（`gen_recall.py` 或并入 `recall_fusion.py`）**，返回格式与 `embedding_recall` 对齐（`{user: {item: score}}`）：

1. 对每个目标用户，取历史 `hist_items` → 映射语义 ID 序列 → 送入生成模型。
2. **beam search（beam=20）**：逐层展开——先取 `code1` 的 top-beam 个候选，每个继续展开 `code2` 的 top-beam，再展开 `code3`，最终得到 beam 条完整语义 ID 路径。
3. 每条路径通过 `sid2item` 反查商品，若路径无对应商品则丢弃。
4. 分数 = 该路径的对数概率累乘（`sum of log P(code_k | prefix)`）。

**接入点**：

- `config.py` 新增：
  - `TIGER_MODEL_FILE = os.path.join(MODEL_PATH, 'tiger_generator.pth')`
  - `TIGER_SEMANTIC_ID_PKL = os.path.join(MODEL_PATH, 'tiger_semantic_ids.pkl')`
  - `RECALL_WEIGHTS['tiger'] = 0.8`（初值，后续 grid search）
- `multi_channel_recall`（`recall_fusion.py:333`）中新增 `tiger_recall_dict`，追加进 `channels` 与 `weights` 列表。
- `merge_recall_results` 的 floor=3 保底机制自动兼容第 5 路，**无需改动融合函数**。

### 7.5 阶段 4：互补性验证（决策闸门）

复用项目既有方法（历史上对 ItemCF vs V2 做过 58.7% 互补性验证）：

1. 单测 TIGER 一路的 HR@100。
2. 测 TIGER 命中集合与 V2 命中集合的 overlap。
3. **决策规则**：
   - 互补性 > 10%（TIGER 独有命中占比）→ 进正式融合，re-tune 五路权重。
   - 互补性 < 10% → 降级为面试素材，不追投 RQ-VAE（不升级方案 A）。

## 8. 关键设计决策与陷阱

| 决策点 | 建议 | 理由 |
|---|---|---|
| codebook 大小 | 256 × 3 层 | 256³≈16.7M 容量，对 25K/137K 商品占用率 <1% |
| 语义 ID 输入源 | `item_embeddings_v2.pkl`（SASRec 微调后） | 比 ALS 原始向量更有语义 |
| 生成模型规模 | 3 层 / 4 头 / 256 维 | 序列短（median 4），无需大模型 |
| 词汇表 | 256（codebook），不是商品数 | 输出空间压缩的关键 |
| 推理解码 | beam search（beam=20） | 逐 token 剪枝，比贪心好、比全量便宜 |
| 时序分割 | 只用 `train_click`，与 V2 一致 | 防验证目标泄露 |

**陷阱清单**：

1. **K-means 层级贪心**：code1 的聚类误差会传导到 code2/code3，无法回溯修正。这是 B 相比 A（RQ-VAE 端到端）的质量损失来源。
2. **语义 ID 碰撞**：多商品同 ID 时 `sid2item` 只留其一，会丢商品；需统计碰撞率，若 >5% 需加码（codebook 提到 512 或加到 4 层）。
3. **短序列冷启动**：历史不足的用户（<2 条）生成模型无上下文，beam search 会退化成全局先验，应归入 Hot/Category 兜底而非硬喂给生成模型。
4. **embedding 版本对齐**：`item2sid` 必须与 `item_embeddings_v2.pkl` 的同一份向量生成；若 V2 重训、embedding 变化，语义 ID 必须重建。
5. **训练/推理 token 一致性**：训练时展平语义 ID 的 token 顺序，必须与推理 beam search 逐层展开的顺序严格一致。

## 9. 止损与升级路径

```
阶段 1 验收失败（code1 无语义分层）
        → 止损：说明当前 embedding 无结构，生成式召回在本场景不成立，不投入后续阶段

阶段 4 互补性 < 10%
        → 降级为面试素材，不进正式 pipeline

阶段 4 互补性 > 10% 且想追前沿
        → 局部升级：仅把 gen_semantic_id.py 的 K-means 换成 RQ-VAE（方案 A）
        → 生成模型 / 训练 / 推理 / 接入代码全部复用
```

---

## 10. 一句话总结

生成式召回对本项目是"换一种读法换互补召回"的探索，不是提精度手段。**先用层次 K-means 造语义 ID 把范式跑通（方案 B），验证互补性这个唯一未知数；通过了再局部升级到 RQ-VAE（方案 A）**。前沿接轨与风险止损被解耦，每步投入都有明确的下一个决策点。
