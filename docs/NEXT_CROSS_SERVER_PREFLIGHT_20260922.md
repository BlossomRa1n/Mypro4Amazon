## 2. 恢复方法与边界

- Medium 实现 `tools/extract_pickle_identity.py`：标准库解析项目 pickle 的编码前缀，验证来源 SHA 和编码 fingerprint，在 `uid` 事件数组前停止；不执行 pickle 对象。恢复 full future、旧 100k 和 corrected legacy 三套编码表。
- Medium 实现 `tools/recover_historical_users.py`：预测 JSON 流式提取 raw 用户，NPZ 仅读 `uid`，必须找到对应 `data_id` 的身份映射；不同编码不直接拼接。来源文件、suite manifest、identity 和原 pickle hash 全部登记，缺失映射留作 unresolved。
- 工具本身检查映射字段格式，不独立证明手工填入的 data_id 与 pickle 一致；本次以原始 data manifest、实际 pickle SHA、编码 fingerprint 和 data_id 交叉验证补足来源链。未来使用时也不能省略这一步。
- 服务器本次执行的是归档中的 v1 工具，旧 `preds_` CSV 通过 `--legacy-users` 显式导入。Ultra 审计发现通用 CSV 识别遗漏 `preds_`，已由 Medium 补齐并增加回归测试。当前本地输出契约同时改为 `schema_version: 1`；已归档 v1 仍保留原貌，不覆写历史证据。
- 本地容量检查读取已有 pickle 的身份、训练索引及窗口边界，丢弃其他状态；`targets()` 被禁止，没有访问未来目标内容、生成候选或计算模型指标。这是代码隔离，不是密码学封存。

当前项目 **74 项自动测试全部通过**（2.878 秒）；本轮新增 7 项覆盖严格编码提取、跨编码 raw-ID 合并、错误映射拒绝、流式解析和 CSV 来源过滤。既有九组 CPU smoke 保持有效；本轮未修改正式 runner 或模型。

## 6. 待批准的最小修订

建议保留 **10 万快速训练、2 万 screen + 8 万 confirm、三个变体 × 三个 seed**，仅将最终 test 改为“完成历史完整性审计后，使用全部剩余合格 fresh 用户 N，冻结名单和 N，再开始开发”。先锁全部 fresh，再优先从历史已评估用户选择 fast-train，避免消耗稀缺 fresh 用户。当前只能保证 **N ≤20,247**，不能承诺一定有足够用户或检验能力。

人数减少会加宽置信区间；且剩余用户可能与被大量评估的用户具有不同活跃度/历史长度分布，最终结论只能针对该 fresh cohort。可在不看未来目标内容的前提下核对历史特征覆盖，但不能利用最终 test 指标挑选人群。若完整审计后样本太少，应等待新数据，不以旧 test 补数。

该建议尚未生效：用户明确指定最终 test 为 10 万，修改人数与验收范围需要用户决定，原因来自该明确约定及实际数据不足，非 skill 的额外审批要求。若坚持 fresh 100k，则必须补充足够从未评估过的新 raw 用户及合格历史/未来窗口，再重新检查来源资产；现有数据无法通过重复采样实现。
